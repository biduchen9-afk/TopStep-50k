# Pre-registration 13 (committed BEFORE the runs): scaling the risk size in the Combine and after the first payout

User request: "Test scaling in the Combine and after payout". Triggers are the ones the user chose for the funded stage in pre-registration 12 (profit milestones, recent performance, time ramp); I add a fourth for the post-payout stage (number of payouts received), which is a milestone of the same kind. The drawdown guard was not chosen and is not tested.

## What the size is today
- Combine: contracts = round(R / ATR) micros with R = $9,600 (a volatility target in dollars per ATR move), capped at 150 micros (15 minis). The size does not depend on the balance, on the progress to the $9,000 target or on recent results.
- After the first payout: contracts = round(a2 x cushion / ATR) with a2 = 0.8 and cushion = remaining balance (the floor is $0 after a payout), so it already moves in proportion to the balance; it does not react to recent results, time since the payout or the number of payouts received. XFA ladder caps apply (30/40/50/100/150 micros at balances 0/1,500/2,000/3,000/4,500).
- Everything else (default split 3 noise-area + 2 gap-VWAP, one Combine open at a time, balanced pre-payout size 1.2 with first payout at $2,000 x 50%, costs, RTH-only, dev-only rule) is unchanged. The stage-1 candidates of pre-registration 12 were NOT adopted and are not used here.

## Engine (all default to None = today's behaviour, tested to be identical)
- `run_eval_firm(..., scale=...)` and `FirmPlan.eval_scale`: the Combine contracts become round(nd x f) with f = 1.0 today. f from the account's own state: `("ladder", ((balance, f), ...))` (f of the highest balance milestone reached, current balance, not sticky), `("perf", L, f_up, f_down)` (last L sessions of the Combine's P&L > 0), `("ramp", d, f_start)` (linear from f_start to 1.0 over the first d sessions), `("const", f)`.
- `FundedPlan.scale2`: the post-payout multiple a2 becomes a function of the account's own state: `("ladder", ((balance, a), ...))`, `("perf", L, f_up, f_down)` (account P&L since the last payout), `("ramp", d, a_start)` (linear from a_start to a2 over d sessions after EACH payout), `("npay", ((n_payouts, a), ...))`.

## Grids (all declared; baseline re-run in the same script)
Combine (22 cells): ladder on the balance, 8 cells = direction {up: f 1.0 -> 1.5 or 2.0; down: f 1.0 -> 0.5 or 0.25} x milestone {$3,000, $6,000}; performance, 6 cells = L {3, 5, 10} x (f_up, f_down) {(1.5, 0.5), (1.25, 0.75)}; ramp, 6 cells = f_start {0.5, 1.5} x d {5, 10, 20}; constant reference, 2 cells = f {0.75, 1.25}.
After the first payout (37 cells; a2 baseline 0.8): ladder on the balance, 16 cells = up: base a2 {0.4, 0.8} x top {1.2, 1.6, 2.4} x milestone {$2,000, $3,500} (12) and down: base {1.2, 1.6} -> 0.4 x milestone {$2,000, $3,500} (4); performance, 8 cells = base {0.8, 1.2} x L {5, 10} x (f_up, f_down) {(1.5, 0.5), (1.25, 0.75)}; ramp after each payout, 6 cells = up: a_start 0.4 -> a2 {0.8, 1.2} over d {10, 20} (4) and down: a_start 1.6 -> 0.8 over d {10, 20} (2); number of payouts, 4 cells = ((2, 1.2), (4, 1.6)), ((2, 0.6), (4, 0.4)), ((3, 1.2),), ((3, 0.5),); constant references, 3 cells = a2 {0.4, 0.6, 1.0}.

## Metrics and acceptance (the "not greedy" rule of pre-registration 9, applied to each stage separately)
Ten 3-year dev farms (starts 2011-2020, default split). Always reported: dev mean, p25, worst, green years, share of funded accounts ever paid, payouts per paid account, number of payouts per paid account, median days to the farm's first payout, seen starts (2021, 2023, 2025-01, 2025-07), full history (not used). Combine cells also report, at account level (sequential starts every 3 sessions 2010-2022, pooled noise x3 + gap x2): Combine pass rate, median days to pass, Combine fees per funded account. Post-payout cells also report the share of funded accounts that die and the mean payouts per funded account.
A cell replaces the current setting only if ALL hold: (1) dev mean AND dev p25 both rise; (2) the worst dev farm is not more than 25% deeper; (3) the share of funded accounts ever paid does not fall by more than 5 points; (4) it beats the baseline's dev mean in BOTH halves of the dev farms (start years 2011-15 and 2016-20); (5) for Combine cells, the Combine fees per funded account do not rise by more than 10% and the median days to the farm's first payout do not rise by more than 10%. Among cells that pass, the highest dev p25 is chosen (ties: higher mean); if none passes, the current setting stays and the closest cell is named. The edge-removed placebo (dev-fitted mean edge removed) is run for the chosen or closest cell.
If a Combine cell AND a post-payout cell both pass, their combination is run once (one extra look) and must itself pass the same rule.

## Honest limits
59 more looks on the same overlapping dev windows (185 declared looks on the sizing questions since pre-registration 11); the grid values are mine, the families and triggers the user's; the Combine is evaluated through its effect on the farm (pass rate and timing change which funded accounts exist and when), so the farm-level numbers carry the path-dependence seen before (full histories swing by $100k+ between neighbouring cells and are not used). Even a pass is "plausible, not proven" and would need a frozen forward test.
